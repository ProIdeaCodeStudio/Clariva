2. HISTORICAL DEVELOPMENT: CLAUDE-ERA FOUNDATION
======================================================================

2.1 Pro Idea website and the initial educational idea

The earlier website work began as a Pro Idea website with a homepage and links to two different service areas: graphic design and educational materials. The user explained that these were contrasting areas and should be separated into distinct websites. This became the architectural/product decision that produced Clariva.

2.2 Initial technical learning and backend decision

The original site began with HTML and CSS, with JavaScript added for interactions and access gating. It became clear that user registration, stored form submissions, access control and email flows could not be securely delivered with static HTML/CSS alone.

Supabase was selected as the backend platform because it provides hosted PostgreSQL, authentication, APIs, storage and server-side functions without requiring the project to run its own always-on server. GitHub Pages remained the static frontend host.

Historical initial backend work included:
- Creating a Supabase project in the West EU (Ireland) region.
- Creating an initial table called "Form Submissions" with identity/contact fields and created_at.
- Connecting the frontend to Supabase using the project URL and a browser-safe publishable key.
- Adding a verification/access process and database-backed records.
- Learning JavaScript through implementation rather than treating the project as a detached tutorial.

Important security correction from the early process: never expose or commit Supabase service-role/secret keys. A Supabase publishable key is intended for browser use but does not secure data by itself. RLS, storage policies, grants and server-side checks are the actual access boundary.

2.3 Early access flow (historical)

The early prototype used a multi-step gate/registration process and a WhatsApp group code verification step. There was a server-side Edge Function named verify-group-code in the early code. The flow also included email notifications, localStorage handling and a database Verified field.

This is historical. Later development moved toward Supabase email confirmation and standard authentication flows, and the WhatsApp-code verification logic was removed/refactored around 7 November 2026. Do not reintroduce the old WhatsApp verification flow without an explicit new decision.

2.4 Branding and naming decisions

7. MANDATORY PASSWORD RESET — NOVEMBER 2026 INCIDENT AND CURRENT STATE
======================================================================

This is the most recent major technical issue and the immediate test priority.

7.1 User requirement

The user requested a password format update and wanted all existing password users to be required to reset their passwords before using the platform. The intended behaviour:
- The requirement is enforced, not optional.
- A user cannot bypass the reset and continue into the student library or admin dashboard.
- The user must follow the normal Supabase password recovery email process.
- The recovery link should lead to reset-password.html and show a new-password form.
- The user can enter the same password again if it meets the current password requirements; the platform should not invent a password-history restriction that Supabase does not provide.
- After successful password update, the mandatory-reset flag is cleared.
- The explanatory text should be short and understandable, explaining that a security update requires a one-time password reset.

7.2 Reported failure

The user experienced a recovery email link that appeared to return to the quick security page instead of displaying the new-password form. The email link did contain a Supabase verification token. The reset URL allowlist had:
- Site URL: https://proideacodestudio.github.io/Clariva/
- Redirect URL: https://proideacodestudio.github.io/Clariva/reset-password.html
- Redirect URL: https://proideacodestudio.github.io/Clariva

The Reset Password email template used {{ .ConfirmationURL }} as the link. Email provider rate limits were also encountered, preventing repeated rapid tests. Custom SMTP was discussed but Gmail account verification/security settings made it impractical at that time; the normal Supabase email provider was used for subsequent testing.

7.3 Implementation work

Repository commits and migrations show work to:
- Add mandatory reset email-link step.
- Require a verified recovery session for reset completion.
- Harden reset RPC permissions.
- Enforce mandatory reset through resource access policies.
- Verify a password change before clearing the reset flag.
- Stage enforcement until frontend deployment.
- Recognise Supabase recovery sessions using the actual OTP AMR rather than assuming an AMR method named "recovery".
- Validate the JWT session ID against auth.sessions and compare it with auth.users.recovery_sent_at.
- Revoke anonymous execution from the recovery-session validation RPC.
- Require a password update before the completion function clears password_reset_required.
